# Technical Source Selection

Read this when grounding claims about software, repositories, languages, frameworks, protocols, APIs, or implementation behavior.

Prefer, as applicable:

1. specifications and official documentation;
2. source code and directly inspected repository implementation;
3. tests or executable behavior;
4. release notes and migration guides for changed behavior;
5. maintainer explanations when implementation intent matters.

Match evidence to the claim. For example, source code may answer what an implementation actually does better than a conceptual guide, while a specification may answer what implementations are required to do.

Community sources are useful for practical experience, failure modes, deployment quirks, and tradeoffs, but should not override direct documentation or observed behavior for a factual API claim without a reason.

For repository learning, verify the relevant branch/commit/version when architecture or code organization may have changed.
